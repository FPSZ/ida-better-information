# ADR-0001：解题地图（Challenge Map）

- 状态：提议（Proposed），待维护者确认
- 日期：2026-10-13
- 适用版本：v2.4 起（在 v2.3.0 的 ports / adapters 结构上实现）
- 代码位置：`src/ibr/analysis/triage.py`（目前是空模块）

## 1. 背景

新手打开一道逆向题，第一个问题通常是"从哪里看起"。本插件已经能给静态程序的 libc 函数命名、在伪代码里注释调用，但还不能回答这个问题。

解题地图的目标：插件跑完之后，给出一份可点击的清单，回答这几件事：

- 程序从哪里开始执行，包括 main 之前就会运行的代码；
- 输入从哪里进来；
- 在哪里做判定，判定时拿什么数据比较；
- 成功和失败分别走到哪里；
- 有没有会改变程序行为的反分析代码。

做方案之前做了两项调研：

1. **题目实测**：用强网杯 2023–2025 的 21 道逆向题做标准答案。其中 15 道是 IDA 能分析的原生程序，6 道是 .NET、字节码、APK 等。
2. **竞品调研**：调查了 27 个相关工具，每条结论都有来源。

原始材料（不随仓库发布）：

- 标准答案：`reverse-skill/work/ibr-challenge-map-research/evidence/gt/*.json|md`
- 探针输出：`evidence/probe/`
- 汇总：`notes/aggregate.md`
- 竞品报告：`notes/competitors.md`

## 2. 调研结论

### 2.1 题目形态：经典 crackme 是少数

15 道原生题按形态分：

| 形态 | 数量 | 题目 |
|---|--:|---|
| 输入 → 比较 → 对/错（经典 crackme） | 3 | Vanguard-ezre, 2023 ezre, Vanguard-babyre |
| 自定义虚拟机 / JIT | 3 | xrtFuze, ez_vm, remem |
| 协议 + 流量包 | 2 | ZZtransfer, iked |
| 模拟器 | 2 | mips（emu + mips_bin） |
| 迷宫 / 游戏 | 1 | boxx |
| 父进程调试子进程（nanomite） | 1 | tradre |
| 只加密不校验（编码器） | 2 | Butterfly, fancy |
| 自修改代码 | 1 | snake |

27 条判定记录里：

| 期望数据的形式 | 条数 |
|---|--:|
| 全局数组 | 11 |
| 根本没有比较 | 7 |
| 栈上立即数拼出来 | 3 |
| 来自外部文件 | 3 |
| 运行时计算 | 3 |

**结论：** 只按"找 memcmp / 找 Correct 字符串"设计，会在大多数题上什么也给不出。地图必须先判断题目形态，再按形态给条目。

### 2.2 一个朴素探针能做到什么

调研时写了一个探针，只用三类信号：按 API 名找调用、按关键词找字符串、找"和全局数据比较"的伪代码行。它在 15 道原生题上的结果：

| 条目 | 找对 |
|---|--:|
| main | 7/15 |
| 输入点 | 7/15 |
| 判定点 | 6/15 |
| **期望数据（密文）** | **0/15** |
| 成功输出 | 6/15 |
| 失败输出 | 7/15 |
| 反分析代码 | 5/11（4 道不适用） |

失败原因按出现频率排列：

1. **main 没找到（8/15）。** 静态程序的 main 没有名字，但有 10 道题都能从 `_start` 里调用 `__libc_start_main` 前装进 rdi 的地址拿到；其余靠 MSVC（`invoke_main`）、MinGW（`__tmainCRTStartup`）和 Rust（`lang_start`）的固定调用链。
2. **main 之前的代码被忽略。** 3 道题的关键代码在 TLS 回调或 `.init_array` 构造函数里。其中 babyre 和 Vanguard-ezre 还会**改写期望数据**，直接导出数组会给出错误的密文。
3. **噪声。** Butterfly 的 100 个关键词字符串里 91 个是 libc 自带文本。boxx、snake 的"反调试"命中全是 C 运行库代码。iked 静态链入的 OpenSSL 没有被 FLIRT 命名，6495 个"用户函数"里混着大量库代码，其中 26 条"反调试"命中都来自 OpenSSL 和 glibc 内部。
4. **头部被篡改的程序直接失效**：ZZtransfer、remem 在 IDA 里是 0 个函数。插件已有 `--repair`，但地图没有利用它。
5. **字符串形态**：短字符串（ez_vm 的 `:)`）被关键词过滤掉；GBK 编码（boxx 的规则说明）没解码；异或后存放的字符串（fancy、mips 模拟器）找不到。
6. **数据流断点**：通过函数指针表调用（Rust）、和栈上立即数比较、代码不在 IDA 函数里（花指令）。
7. **题目附带的文件决定了解法**（9/21）：pcap、VM 程序文件、密文文件、`.abc` 字节码、追加在 PE 尾部的 zip。只看二进制本身不够。

### 2.3 竞品：没有工具做这件事

| 能力 | 现有工具 | 不足 |
|---|---|---|
| 输入 → 判定 → 成功/失败的整体地图 | 无 | 中英文搜索都只找到手工流程（字符串 → 交叉引用 → main） |
| 导出比较用的字节 | findcrypt 只导出已知密码常量；IDA Shift+E 要手选 | 没有工具取 memcmp / 循环比较的操作数 |
| 反分析检测 | capa（Windows 为主）、AntiDebugSeeker（仅 Windows）、DiE（PE） | Linux 静态检测基本空白；都依赖函数名 |
| 交给求解器 | AngryIDA、IDAngr、SENinja、Ponce | 都要手选地址；angr 的自动 libc hook 只对未 strip 的程序有效 |
| 给 AI 用 | ida-pro-mcp、Hex-Rays 官方 MCP（2026-09 公布）、Binary Ninja Sidekick | 是通用工具接口，没有"解题地图"这种高层结论 |

关键事实（来源见竞品报告 §2.1）：capa 在 IDA 里只认有名字的函数，包括 `FUNC_LIB` 或不以 `sub_` 开头的函数。所以在静态程序上，本插件的 FLIRT 命名是 capa 这类工具的**前提**，而不是重复。

## 3. 决策驱动因素

1. **新手可用**：条目要能直接点到地址，文字说"这里在干什么"，不堆原始数据。
2. **准确优先于全面**：错的密文比没有密文更糟（见 babyre）。不确定的条目要标出来。
3. **静态、离线**：不运行题目程序（安全），不联网。
4. **复用已有长处**：libc 命名、调用注释、ELF 修复、ports 结构。
5. **可测**：核心逻辑写在 ports 后面，用这 21 道题做回归。
6. **速度**：中小程序几秒内出结果，大程序有上限，不卡 IDA。
7. **能给机器读**：同一份结果输出成 JSON，供以后的 AI 接口（`adapters/agent.py`）使用。

## 4. 备选方案

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A. 规则清单 | 按 API 名 + 关键词字符串列条目（即调研探针） | 简单、快 | 实测期望数据 0/15、main 7/15，噪声大，不懂题目形态 | 不采用，作为基线 |
| B. 接入 capa 规则引擎 | 把 capa 当依赖，复用其规则 | Windows 反分析规则现成 | 新增重依赖；没有数据流，取不到比较操作数；Linux 规则空白 | 不作依赖；借鉴其规则格式与"跳过库代码"的经验 |
| C. 符号 / 模拟执行 | 用 angr、Unicorn 求出成功路径 | 能直接出解 | 依赖重、慢；VM、协议题效果差；超出插件定位 | 不做；只导出给求解器的骨架（见 §5.9） |
| D. 交给大模型 | 把反编译结果丢给 LLM 找关键点 | 灵活 | 结果不可复现、难测；数字易错；需要联网或本地模型 | 不作核心；通过 JSON 接口配合 |
| **E. 先分类、再收集证据、再推断角色** | 预检题目形态 → 找入口和 main 之前的代码 → 收集带出处的证据 → 推断每个位置的角色并打分 → 输出 | 覆盖多种形态；每条结论都有证据，可回归测试；纯 Python，可在 ports 后实现 | 规则要随题型扩充；VM、协议题只能给到"关键位置"，给不了解 | **采用** |

## 5. 决策：方案 E

### 5.1 范围

v1 包含：

- **目标预检**：原生 / .NET / APK / 字节码 / 附带文件；头部是否被篡改；是否加壳。
- **入口**：main 以及 main 之前会运行的代码（TLS 回调、`.init_array`、`.ctors`）。
- **输入点**：API 调用、`argv`、读文件。
- **判定点**：库函数比较、循环逐字节比较、长度检查、计数器判定。
- **期望数据**：导出字节，并检查是否有其他代码写它。
- **成功 / 失败出口**：字符串及其分支。
- **反分析标记**：只标出位置和影响，见 §5.4 R7。
- **题目形态提示**：VM 分发器、JIT、编码器、协议、模拟器、启动器。

不做（非目标）：

- 求解、去混淆（控制流平坦化）、VM 指令还原。VM 指令还原另立 ADR，对应 `analysis/vm.py`。
- 运行或调试题目程序。
- 自动修改程序字节。
- .NET、APK、字节码内部的分析：只识别出来，并告诉用户换什么工具。

### 5.2 处理流程

```
预检(target) ──> 入口(entry) ──> 证据收集(evidence) ──> 角色推断(roles) ──> 排序(rank) ──> 输出
   │                │                 │                        │                  │
   │ 形态/附带文件    │ main + 前置代码    │ 调用/字符串/比较/       │ input/check/      │ 去噪、可达性、
   │ 头部篡改→修复    │                 │ 立即数/指令/写者        │ expected/win/fail  │ 置信度
```

1. **预检**：读文件头和同目录文件（只读）。头部被篡改时，提示用 `--repair` 后重新加载，地图本身不改文件。.NET（CLI 头）、APK、Ark `.abc`、EVM 字节码、PE 尾部追加的 zip 只出一条"形态 + 建议工具"。
2. **入口**：
   - 有名字的 main / WinMain 直接用；
   - 静态 ELF 取 `_start` 里调用 `__libc_start_main(_impl)` 前装进 rdi 的地址；
   - MSVC 走 `__scrt_common_main_seh → invoke_main`，MinGW 走 `__tmainCRTStartup`，Rust 取 `lang_start` 前装进 rdi 的地址；
   - 再列出 TLS 目录和 `.init_array` 里属于用户代码的函数，标为"main 之前运行"。
3. **证据收集**：每条证据带地址和出处，类型包括：
   - 调用了哪个已识别函数；
   - 引用了哪个字符串；
   - 伪代码里的比较表达式；
   - 写入全局变量的指令；
   - 可疑指令的密度；
   - 大型 switch 结构。
   证据只从"用户代码"收集：排除 `FUNC_LIB`、导入跳板，以及本插件识别出的 libc / 运行库函数。
4. **角色推断**：用规则把证据组合成角色（规则见 §5.4），每个角色带置信度：确定 / 很可能 / 线索。
5. **排序**：从入口沿调用图计算可达性和距离。不可达的函数降级，但不删除（boxx 的渲染函数就是不可达的死代码，却是关键线索）。
6. **输出**：IDA 里的列表窗口，JSON，以及可选的伪代码注释。

### 5.3 数据模型（core，纯 Python）

```python
MapEntry(
  role,        # entry | pre_main | input | check | expected | success | failure |
               # anti_analysis | shape | companion | note
  ea, func,    # 地址与所在函数（可为空：附带文件、形态提示）
  title,       # 一行说明（中英文，走 i18n）
  detail,      # 补充：比较的长度、数据形式、写者列表……
  confidence,  # "sure" | "likely" | "hint"
  evidence,    # [Evidence(kind, ea, text)]：为什么这么判断
  data,        # 期望数据：{"ea", "len", "bytes", "form", "writers": [...]}
)
```

借鉴（来源见竞品报告 §4）：

- Malcat 检测器的"级别 + 类别"；
- DiE / cracklab 区分"规则确认"和"启发式"；
- findcrypt 列表里的 Hex 列。

### 5.4 v1 规则

| 编号 | 角色 | 信号 | 实测依据（题目） |
|---|---|---|---|
| R1 | entry | 见 §5.2 第 2 步 | 10 道靠 `__libc_start_main`，3 道靠 CRT 名称，1 道靠 Rust，1 道靠 MSVC 调用链 |
| R2 | pre_main | TLS 目录、`.init_array`、`.ctors` 中的用户函数 | babyre、Vanguard-ezre、ezre |
| R3 | input | 已识别输入函数的调用点（含 `getline`、C++ `istream`）；`argv[n]` 被读取；文件读取后进入用户代码 | ez_vm 用 argv[1]，xrtFuze、Butterfly 读文件 |
| R4 | check | memcmp/strcmp 类调用，取两个操作数；`a[i] != b[i]` 形式的循环比较；与常量比较的长度检查；全局计数器判零 | Vanguard-ezre、babyre、ez_vm、boxx |
| R5 | expected | R4 中非输入一侧的操作数：全局数组按循环上界或长度取字节；栈立即数按写入顺序拼起来；同时列出该数据的所有写者，有写者就标"运行时会被修改" | 11 个全局数组、3 个栈常量；babyre、Vanguard-ezre 有写者 |
| R6 | success / failure | 判定分支两侧的输出调用及其字符串参数；关键词表含中文，短字符串只要紧邻判定就保留；GBK 回退解码 | ez_vm 的 `:)`、boxx 的 GBK 字符串 |
| R7 | anti_analysis | 只标位置和对程序的影响，不给处理办法。在用户代码里出现的：读调试器状态（API 或 PEB 字段）、`/proc/self/status`、`ptrace`、父子进程调试关系、大量 `int3`、时间差判断。若在 main 之前运行或会写入期望数据，单独提示 | 6/15 题有，其中 3 题在 main 之前，2 题会改写期望数据 |
| R8 | shape | 大型 switch + 程序计数器自增 → 虚拟机分发器；mmap/mprotect 可执行 + 间接调用 → JIT / 自修改；读文件 → 循环变换 → 写文件，且没有判定 → 编码器；send/recv + 端口常量 → 协议；嵌入解释器的 API → 启动器 | xrtFuze、ez_vm、remem、snake、Butterfly、fancy、ZZtransfer、iked、ABabyChal |
| R9 | companion | 同目录文件按文件头识别类型；在附带文件里搜索程序中的 4/8 字节常量 | iked 的常量与 pcap 的 SPI 一致；Butterfly 的 encode.dat |

### 5.5 降噪（来自实测）

- **库代码一律不算用户代码**：FLIRT 识别出的函数、libc 断言字符串所在函数，以及调用链只通向库的函数。这一条能去掉 Butterfly 那 91 条 libc 字符串。
- **运行库自带的调用不算反分析**：C 运行库的异常过滤器、malloc 初始化里的取时间、Rust 运行库的信号处理。
- **按调用位置判断**：只报告在用户函数里的调用（借鉴 capa 不报 `IsDebuggerPresent` 的做法）。
- **大程序折叠**：未命名的大块库代码（OpenSSL、Rust std）折叠成一条"静态库代码"。

### 5.6 期望数据的导出

- **格式**与 IDA Shift+E 一致：十六进制、Python `bytes`、C 数组。
- **长度**取循环上界、memcmp 的长度参数或 `strlen` 的比较值；推不出来就只给起始地址，并标为"长度未知"。
- **有写者时不给"干净"的字节**：列出写者（包括 main 之前的代码）并标"运行时会被修改"，避免 babyre 那种拿到错误密文的情况。
- 只读取数据库里的字节，不执行任何代码。

### 5.7 端口变更

`ports.Program` 新增：

- `xrefs_to(ea)` / `xrefs_from(ea)`（区分读、写、调用）；
- `strings()`；
- `entry_points()`；
- `tls_callbacks()`、`init_array()`；
- `segment_of(ea)`；
- `bytes(ea, n)`；
- `imports()`；
- `sibling_files()`：只读，列出题目目录下的文件。

`ports.Decompiler` 新增 `function_tree(ea)`：返回整个函数的中立语法树（语句、if/while/for、赋值、比较、下标、调用），不再只给调用表达式。`analysis/algo.py` 和 `analysis/vm.py` 以后也用这一份接口。

`core/` 和 `app/` 仍不允许 import IDA，由 `tests/test_architecture.py` 检查。

### 5.8 界面

- 面板加一个"解题地图"按钮，打开 IDA 的列表窗口（`ida_kernwin.Choose`）。
- 列：角色 | 地址 | 函数 | 说明 | 置信度。双击跳转。
- 期望数据条目右键可以复制为十六进制、Python 或 C 数组。
- 第一行永远是形态提示，例如"自定义虚拟机：分发器在 sub_8048863"或"这是 .NET 程序，请用 dnSpy"。
- 可选：把每条结论作为注释写到对应地址。复用现有日志，撤回时一并移除。
- 中英文跟随面板语言。

### 5.9 对外输出

- **JSON**：同一份 `MapEntry` 列表加版本号。供命令行 `--map`（通过 idalib 无界面运行）和以后的 AI 接口使用。地址统一写成十六进制字符串，因为大模型容易算错数字（ida-pro-mcp 的文档也提醒了这一点）。
- **求解器骨架（v2，可选）**：
  - 用成功 / 失败地址生成 angr 脚本的 find / avoid；
  - 对插件识别出的 libc 函数地址加 hook，补上 angr 在 strip 过的程序上做不到的部分；
  - 只生成文本，不运行。

### 5.10 性能

- 证据收集以交叉引用为种子：只反编译入口、种子函数，以及从入口出发 2 层以内的函数，上限 60 个函数或 20 秒。
- 超过上限时，列表里写明"已截断"。
- 实测参考：调研探针在 18 道题上反编译最多 40 个函数，大部分 2–10 秒，最大的 emu 约 70 秒（含分析）。

## 6. 评估

- **回归集**：21 道题的标准答案（JSON）放进 `tests/fixtures/challenge_map/`。只放结论和地址，不放题目二进制。在 idalib 上跑完整地图，与标准答案比对。
- **指标**：每个角色的召回率和误报数。期望数据要求字节完全一致，或正确标出"运行时会被修改"。

| 指标（15 道原生题） | 基线 | v1 目标 |
|---|--:|--:|
| main | 7/15 | 15/15 |
| 输入点 | 7/15 | ≥ 12/15 |
| 判定点（有判定的题） | 6/15 | ≥ 10/15 |
| 期望数据 | 0/15 | 可静态导出的题 ≥ 7，有写者的题全部标出 |
| 成功 / 失败出口 | 6/15 / 7/15 | ≥ 11/15 |
| 形态提示 | 无 | VM、编码器、协议、模拟器、非原生题全部给出 |
| 每题误报 | — | 角色为"确定"的条目没有误报 |

- **单元测试**：规则写在 core 里，用 `tests/fakes.py` 构造的语法树测试，不需要 IDA，几秒跑完。
- **整体审计**：插件跑前跑后，伪代码整体（包括变量名）要不变，地图只读。这一条来自 2026-10-13 的教训：当时只比对了注释，没有比对伪代码其余部分。

## 7. 后果

正面：

- 填补了竞品空白：整体地图、比较字节导出、Linux 反分析标记、形态提示。
- 把插件已有的 libc 命名转化成新手能直接用的结论。
- JSON 输出为 AI 接口和求解器骨架打好基础。

负面 / 代价：

- 规则需要维护，新题型要补规则。用回归集控制退化。
- 需要扩充 ports，并新增中立语法树的适配层。工作量主要在 `adapters/ida/ctree.py`。
- VM、协议、模拟器题只能给出关键位置，新手可能期待更多，界面上要写清楚。
- 回归集只有 21 道题，可能过拟合强网杯风格；需要补充其他比赛的题目。
